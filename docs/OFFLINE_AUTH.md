# Onboarding and offline authentication

Roboff uses Roborock's HTTPS account API during setup to retrieve vacuum local keys and home/room information. Once setup is complete, discovery, status, maintenance, and control communicate directly with the vacuum on Wi-Fi. There is no MQTT transport or automatic cloud fallback.

## Account setup

The reference API offers password login and emailed-code login as alternatives. It does not document an implemented password-then-code two-factor sequence. The modern emailed-code flow discovers the account region, sends a code, obtains a signing key and current agreement version, then exchanges the entered code for a temporary account session. Password login uses the reference's older password endpoint. Accounts that require an updated user agreement must accept it in the official Roborock app. These behaviors follow the supplied source and [Python-roborock API documentation](https://python-roborock.github.io/python-roborock/roborock/web_api.html).

Setup uses that temporary session to fetch the account's home catalog, devices, local keys, models, and room names. The user selects the vacuums to import. A cloud device record can be saved before its local IP address is known; LAN discovery supplies the address when the vacuum is reachable.

Only local keys and the metadata needed offline are saved. Account passwords, email verification codes, account tokens, and cloud signing credentials are not stored as application preferences or exported files. Setup errors do not include response bodies or credential values. Reopening account setup requires signing in again.

The API reference returns a home identifier and that home's catalog; the app does not claim to enumerate an arbitrary list of houses. Shared-device records may be limited by the owner's sharing permissions. A device lacking a usable local key cannot be paired for LAN control.

## Home and room names offline

The cloud catalog provides home/room display names and opaque room identifiers. The local `get_room_mapping` command supplies the robot's segment-to-room-ID mapping. Roboff joins these identifiers to display imported names without another cloud request. Local room-name overrides take precedence. Unmapped or newly created segments use a numeric fallback until names are imported again or assigned in the app.

Imported names are snapshots. Changing room names in the official app does not cause Roboff to open a cloud connection in the background. Rerun account setup to refresh the keys and metadata. Robot maps remain outside scope because the supplied S8 implementation obtains them through MQTT.

## Manual setup without cloud access

Stock S8 firmware needs a device-specific `localKey` for local commands. Discovery reveals an address and sometimes the device identifier; it cannot reveal that key. If the owner already holds the key, manual pairing remains available: select a discovered vacuum or enter its local IP, enter the existing 16-byte key, and choose **Save & connect**.

The key is literal UTF-8 text, not hex-decoded. Saving a pairing encrypts it, then the app validates the connection by reading the vacuum's status. A saved record alone does not establish that a key or address is correct. Factory-resetting or reprovisioning the vacuum may replace its key.

No configuration file, Python environment, serial provisioning utility, or continuous cloud access is required by the Android app.

## Storage and transport

`RobotStore` encrypts saved profiles, including local keys, home information, and room names, using AES-256-GCM with a fresh random IV for each write. The encryption key is generated by Android Keystore and is not exported. Encrypted records are private to the application. Backups and device-transfer backups are disabled.

Secret input fields are masked and excluded from view-state saving; Android autofill hints identify the account password and emailed code. Passwords and email codes remain in memory only while their setup step needs them. Removing a vacuum removes its saved profile. Clearing application data or uninstalling the app removes saved pairings; the owner can sign in or enter a local key again.

Cloud setup uses TLS to approved Roborock endpoints, with redirects disabled and bounded network operations. Local control uses the Roborock firmware's V1/L01 protocol; its wire cryptography is separate from Roboff's at-rest encryption. The control command allowlist contains no cloud operations.
